# 10. 운영 전 코드 감사

> 실행: 2026-09
> 되돌릴 지점: `pre-audit-backup` 브랜치
> 결과: 검증 **401건** 전부 통과 · typecheck · build 통과

새 기능을 더 붙이기 전에 **돈이 틀리게 계산되는 곳**과 **데이터가 망가질 수 있는 곳**을
먼저 찾아 고쳤습니다. 아래는 실제로 재현한 버그와 고친 뒤 숫자입니다.

## 발견한 실제 버그

### 🔴 1. 송금수수료가 통장에서 두 번 빠졌다

`createRemittance` 가 `remittance.bankFeeKrw` 에도 저장하고 `BANK_FEE` 지출 전표도
만드는데, `accountBalances` 가 둘 다 뺐습니다.

```
수수료 15,000 인 1,000,000 송금
  고치기 전   통장에서 1,030,000 차감   ← 수수료 두 번
  고친 뒤     통장에서 1,015,000 차감   ✓
```

`BANK_FEE` 전표는 손익 집계에 필요하므로 그대로 두고, 잔액 계산에서만 빼지 않습니다.

### 🔴 2. 급여를 다시 입력하면 사회보험이 두 번 잡혔다

급여 전표는 `payroll.expenseId` 로 연결돼 있어 취소되는데, 사회보험 전표는 연결이 없어
옛것이 살아남았습니다.

```
2019-07 사회보험 1,416 → 1,500 으로 정정
  고치기 전   전표 2건 · 합계 2,916   (1,416 + 1,500)
  고친 뒤     전표 1건 · 합계 1,500  ✓
```

### 🔴 3. 고객 예치금보다 많이 송금할 수 있었다

```
예치금 1,000,000 · 송금완료 600,000 · 남은 400,000
  고치기 전   500,000 추가 송금이 그대로 저장됨 (예치금 −100,000)
  고친 뒤     「남은 금액 400,000원, 쓰려는 금액 500,000원 — 100,000원 부족합니다」
```

세 겹으로 막습니다.
1. 애플리케이션에서 확인하고 얼마가 모자란지 알려 준다
2. 거래처 단위 자문 잠금(`pg_advisory_xact_lock`) — 동시에 두 사람이 넣어도 안전
3. DB 제약 트리거(`003_deposit_guard.sql`) — 애플리케이션을 건너뛰어도 막힌다

점검한 경로는 해외송금 · 일반예치금 사용 · 환불 · 조정 넷인데, 전부 같은 원장을 지나므로
트리거 하나로 덮입니다.

초과송금을 **숨기지 않습니다**. `remitPending` 을 0으로 자르되 `remitExcess` 를 따로 남기고
상태를 `OVER` 로 표시합니다. `findDepositAnomalies()` 로 마이너스 잔액을 찾아냅니다.

### 🔴 4. 작성중(DRAFT) 송금이 이미 돈을 빼고 있었다

아직 은행에 넣지도 않은 전표가 예치금을 줄이고 통장 잔액을 깎았습니다.

```
DRAFT ─(송금완료)→ SENT ─(도착확인)→ ARRIVED,  각 단계에서 취소 가능
```

| 상태 | 예치금 | 한국 통장 | 수수료 전표 |
|------|--------|----------|------------|
| DRAFT | 영향 없음 | 영향 없음 | 안 만듦 |
| SENT | 차감 | 차감 | 만듦 |
| ARRIVED | (유지) | (유지) | (유지) |
| CANCELLED | 반대부호로 복원 | 복원 | 취소 |

- `CANCELLED` 상태로는 새로 만들 수 없습니다.
- DRAFT 를 취소하면서 예치금을 되돌리면 **있지도 않던 돈이 생겨납니다.** 실제로 뺀 전표만 되돌립니다.
- 상태 전환은 서버에서 강제하고, 화면도 상태에 맞는 버튼만 보여 줍니다.

### 🔴 5. 실제 도착금액이 바뀌어도 주문별 CNY 가 그대로였다

`markArrived` 가 송금 전표만 고치고 배분은 안 건드려, 주문별 원가가 실제와 어긋났습니다.

```
KRW 600,000 / 400,000 인 두 주문, 실제 도착 CNY 4,987.35
  고치기 전   배분 합계 5,000 (등록 당시 값 그대로)
  고친 뒤     2,992.41 + 1,994.94 = 4,987.35  ✓
```

`src/lib/allocate.ts` — 비율 배분. 반올림 잔여는 **비중이 가장 큰 쪽**에 얹습니다.
마지막 항목에 얹으면 목록 순서만 바뀌어도 결과가 달라져 재현이 안 됩니다.

### 🔴 6. 세금계산서 안전장치가 없었다

| 문제 | 고친 뒤 |
|------|--------|
| 세무 규칙이 다른 주문이 한 장에 묶였다 | `invoiceBase`·`vatMode`·`vatRate`·`rounding`·`accountingClass`·거래처를 대조해 막고, **어느 주문이 어떻게 다른지** 짚어 준다 |
| 이미 계산서에 들어간 주문을 또 넣을 수 있었다 | 차단 |
| 주문별 금액을 N등분했다 | 실제 발행 대상금액 비율대로 배분 |
| 취소하면 무조건 미발행으로 되돌렸다 | 살아있는 다른 계산서의 상태를 따라간다 |

```
공급가액 1,000,000 + 3,000,000 을 한 장에
  고치기 전   2,000,000 / 2,000,000   ← 주문별 매출이 틀어진다
  고친 뒤     1,000,000 / 3,000,000  ✓
```

### 🔴 7. 과거 달의 숫자가 나중에 바뀌었다

`orderDate` 가 그 달인 주문을 가져와 그 주문의 **전 생애** 입금·지출을 합산하고 있었습니다.

```
5월 주문에 5월 입금 1,000,000 → 5월 매출 1,000,000
같은 주문에 6월 입금 500,000 을 추가하면
  고치기 전   5월 매출 1,500,000  ← 끝난 달이 바뀐다 / 6월 매출 0
  고친 뒤     5월 매출 1,000,000  ✓ / 6월 매출 500,000  ✓
```

화면을 두 갈래로 나눴습니다. 뜻이 다른 숫자를 한 칸에 두면 안 됩니다.

| | 「이 달 손익」 | 「이 달에 시작한 주문의 수익성」 |
|---|---|---|
| 기준 | 전표에 적힌 날짜 | 주문 |
| 답하는 질문 | 이 달에 얼마 벌었나 | 이 달에 받은 일이 남는 장사였나 |
| 나중에 바뀌나 | **아니오** | 예 (거래가 붙으면) |
| 입금 없는 주문의 비용 | 포함 (돈은 실제로 나갔다) | 제외 |

`fundsSnapshot(asOf)` 의 as-of 누수도 전부 잡았습니다.

- `listReceivables()` 가 `asOf` 를 안 받아 과거 시점에 미래 입금이 섞였다
- `latestFxRate()` 가 항상 오늘 환율을 써서 지난 달 잔액이 오늘마다 바뀌었다
- `summarizeOrders()` 에 `asOf` 추가
- `listUnbilledVat(asOf)` — 그 달까지 받은 부가세만

> ⚠ 지급여부(`PAID`/`PLANNED`)는 현재 상태만 있고 변경 이력이 없어, 과거 시점 조회에서도
> 「지금 미지급인 것」을 셉니다. 코드에 명시해 두었습니다.

### 🔴 8. 세션이 12시간 동안 옛 권한을 유지했다

| 문제 | 고친 뒤 |
|------|--------|
| JWT 안의 권한을 12시간 믿었다 | 요청마다 DB에서 활성 여부·현재 권한을 다시 본다 |
| 비밀번호를 바꿔도 기존 세션이 살아 있었다 | `users.sessions_valid_from` 으로 그 이전 토큰을 즉시 무효화 |
| 계정을 정지해도 열어 둔 창으로 계속 썼다 | 정지·해제 때도 세션 무효화 |
| 로그인 실패 제한이 없었다 | 연속 5회 실패 시 15분 잠금. 없는 아이디는 세지 않는다 |
| 시드가 기본 비밀번호를 쓰고 콘솔에 찍었다 | 운영에서는 `SEED_ADMIN_PASSWORD` 없이 설치 중단. 비밀번호는 찍지 않는다 |

### 🔴 9. 기준정보를 바꾸면 과거가 소급해서 달라졌다

- **계좌**: 거래가 붙은 뒤에도 소속·루트·통화를 바꿀 수 있었습니다.
  원화 계좌를 위안 계좌로 바꾸면 지난 입금이 전부 위안이 됩니다. → 차단. 비활성 후 새 계좌 안내.
- **거래유형**: 사용 중인데도 세무 규칙을 바꿀 수 있었습니다.
  이미 신고한 달의 부가세가 조용히 달라집니다. → 차단. 새 유형을 만들어 쓰도록 안내.
- **주문 등록**: 계좌와 루트·거래유형이 맞는지 서버가 확인하지 않았습니다.
  법인통장 거래를 중국 계좌에 꽂을 수 있었습니다. → 대조해 막음.

이름·은행·계좌번호·기초잔액·정렬순서·메모 같은 **뜻이 바뀌지 않는 항목은 그대로 바꿀 수 있습니다.**

### 🔴 10. 검증이 운영 DB에 테스트 데이터를 만들었다

`npm run verify` 가 `DATABASE_URL` 의 DB에 주문·입금·지출을 만들었다 지웠습니다.

- `TEST_DATABASE_URL` 을 따로 요구합니다. 없으면 시작조차 하지 않습니다.
- DB 이름이 `prod`/`production`/`live`/`운영` 이면 중단합니다.
- `test` 계열 이름이 아니면 `ALLOW_TEST_ON_THIS_DB=<이름>` 을 명시해야 돕니다.

겸사겸사 드러난 것: **기존 281건은 DB 상태에 기대고 있었습니다.**
빈 DB면 phase5 가 죽고(환율을 구할 입금이 없음), 시연 데이터가 있으면 phase6 이
4건 틀렸습니다(외부관리번호 충돌). 둘 다 자급자족하게 고쳤습니다.

### 11. 부가세 예수금 — 신고·납부 개념이 없었다

받은 부가세를 처음부터 전부 누적해 빼고 있어, 이미 낸 부가세까지 영원히 회사 돈이
아닌 것으로 잡혔습니다. 대표님 확인을 받아 **신고기간별 정산**으로 구현했습니다.
자세한 내용은 [04. 계산 공식 12장](04-계산공식.md) 참고.

  ON payrolls (insurance_expense_id);

-- 세션 무효화 · 로그인 잠금
ALTER TABLE users
  ADD COLUMN sessions_valid_from TIMESTAMPTZ NOT NULL DEFAULT now(),
