# 07. 변경이력·감사 설계

> **돈을 다루는 프로그램**이므로 "지우고 다시 계산"을 구조적으로 불가능하게 만듭니다.

---

## 1. 무삭제(No-Delete) 원칙

| 대상 | 삭제 정책 |
|------|----------|
| `orders`, `receipts`, `expenses`, `remittances`, `invoices` | **물리 삭제 금지.** `is_void = TRUE` + 사유 기록 |
| `deposit_ledger` | **UPDATE/DELETE 자체를 DB RULE로 차단** (append-only). 정정은 반대부호 상쇄행 추가 |
| `partners`, `accounts`, `deal_types` 등 마스터 | 삭제 대신 `is_active = FALSE` (이미 사용된 마스터는 비활성화만 가능) |
| `change_logs` | 삭제·수정 불가 (INSERT 전용) |

```sql
-- 예치금 원장 불변 보장
CREATE RULE deposit_ledger_no_update AS ON UPDATE TO deposit_ledger DO INSTEAD NOTHING;
CREATE RULE deposit_ledger_no_delete AS ON DELETE TO deposit_ledger DO INSTEAD NOTHING;

-- 변경이력 불변 보장
REVOKE UPDATE, DELETE ON change_logs FROM app_user;
```

## 2. 변경이력 기록 방식

**기록 단위: 필드 하나당 1행**

| 필드 | 값 예시 |
|------|--------|
| table_name | `expenses` |
| record_id | `4821` |
| action | `UPDATE` |
| field_name | `amount` |
| **old_value (이전 값)** | `15000.00` |
| **new_value (변경된 값)** | `15500.00` |
| **changed_by (수정자)** | `박직원 (user_id=7)` |
| **changed_at (수정시각)** | `2026-05-12 14:22:03+09` |
| reason | `공장 단가 정정` |
| request_id | `a3f2...` (한 번의 저장을 묶는 ID) |

### 기록 대상 action

| action | 발생 시점 |
|--------|----------|
| `CREATE` | 전표 생성 (전체 값을 JSON으로 new_value에 기록) |
| `UPDATE` | 필드 변경 (변경된 필드만 각각 1행) |
| `VOID` | 취소 처리 |
| `RESTORE` | 취소 복구 (OWNER만) |
| `SETTLE` | 주문 정산완료 확정 |
| `UNLOCK` | 정산완료 주문 잠금해제 ⚠️ 별도 모니터링 |
| `IMPORT` | 엑셀 가져오기로 생성 |
| `LOGIN` / `EXPORT` | 접속·내보내기 (감사용) |

### 구현 방식

애플리케이션 레이어(ORM 미들웨어)에서 **저장 직전 old/new 비교** 후 자동 기록합니다.
개발자가 빠뜨릴 수 없도록 저장 함수를 단일 게이트로 강제합니다.

```ts
// 모든 금액성 테이블 저장은 이 함수만 통과
await auditedSave({
  table: 'expenses',
  id: 4821,
  patch: { amount: 15500 },
  reason: '공장 단가 정정',   // 금액 필드 변경 시 필수 — 없으면 예외
  user: currentUser,
})
```

**사유 필수 필드 목록**

| 테이블 | 사유 필수 필드 |
|--------|--------------|
| receipts | amount, fx_rate, receipt_date, partner_id |
| expenses | amount, fx_rate, category_id, payment_status |
| remittances | krw_amount, cny_arrival_amount, status |
| invoices | target_amount, supply_amount, vat_amount, issue_status |
| deposit_ledger | (ADJUST / REFUND 행은 reason 없이 생성 불가) |

## 3. 취소(VOID) 처리 시 연쇄 규칙

```
송금 전표 취소
 ├ remittances.is_void = TRUE
 ├ remittance_allocations 는 그대로 둠 (이력)
 └ deposit_ledger 에 상쇄행 INSERT
      movement = 'ADJUST', amount_krw = +600,000
      reason = 'RM-2026-000012 취소에 따른 복원'
      ref_table='remittances', ref_id=12
```

```
입금 전표 취소
 ├ receipts.is_void = TRUE
 ├ receipt_splits 유지
 ├ deposit_ledger 상쇄행 (예치금 분해가 있었던 경우)
 └ 주문 마진 자동 재계산
```

```
지출 전표 취소
 ├ expenses.is_void = TRUE
 ├ expense_allocations 유지 (집계에서는 is_void 로 제외)
 └ 연결 주문 마진 자동 재계산
```

> 취소된 전표는 목록에서 **취소선 + 회색**으로 표시되며, "취소 포함 보기" 토글로 확인합니다.

## 4. 주문 잠금 (정산완료)

```
OPEN (진행중)
  └─ [정산완료 처리] → SETTLED
        · 하위 전표 추가/수정/취소 차단
        · 마진 확정값 스냅샷 저장 (settled_margin, settled_at)
        · change_logs: action=SETTLE

SETTLED
  └─ [잠금해제] (MANAGER 이상 + 사유 필수) → OPEN
        · change_logs: action=UNLOCK
        · 대시보드 "이번 달 잠금해제 N건" 으로 노출 (관리 신호)
```

## 5. 대시보드 수치의 재현 가능성

| 요구 | 구현 |
|------|------|
| "작년 5월 대시보드를 지금 다시 봐도 같아야 한다" | 모든 집계가 **전표 발생일 기준**이므로 재계산 시 동일 |
| "환율이 바뀌어도 과거 수치가 변하면 안 된다" | 환산액을 전표에 **저장**하므로 사후 환율 변경 영향 없음 |
| "정산완료 주문 마진은 고정되어야 한다" | `SETTLED` 시 마진 스냅샷 저장 + 재계산값과 불일치 시 경고 |

**월 마감(선택 기능)**
- 월 단위 `period_close` 처리 시 해당 월 전표 전체 잠금
- 마감 후 수정은 OWNER 승인 + `UNLOCK` 이력

## 6. 접근 감사

| 항목 | 기록 |
|------|------|
| 로그인/로그아웃 | user, IP, 시각 |
| 데이터 내보내기(엑셀) | 대상 화면, 행 수, 사용자 |
| 급여 화면 조회 | OWNER/MANAGER만 접근, 조회 이력 기록 |
| 잠금해제 | 별도 알림 (대시보드 배지) |
