# 05. 거래 흐름 (실제 업무 시나리오)

> 각 루트에서 실제로 어떤 순서로 데이터가 쌓이고, 시스템이 무엇을 자동 처리하는지 정리합니다.

---

## 시나리오 A. 해외송금 루트 (중국법인 직접 수취)

**상황**: 5/1 △△무역이 중국법인 계좌로 CNY 25,000 도착 (USD 인보이스 3,500). 이후 상품비·검품비가 나눠서 발생.

| 날짜 | 업무 | 시스템 처리 |
|------|------|------------|
| 5/1 | 새 거래 등록 → △△무역 / 해외송금 | `orders` 생성 (`ORDER-2026-000127`, entity=`CN`, settlement_currency=`CNY`) |
| | CNY 도착금액 25,000 / USD 인보이스 3,500 입력 | `receipts` (amount=25,000 CNY, usd_amount=3,500) <br> `receipt_splits` (SALES 25,000) |
| 5/3 | 상품대금 CNY 15,000 지급 | `expenses` + `expense_allocations` → 주문 귀속 |
| 5/5 | 검품비 CNY 1,000 | 동일 |
| 5/8 | 추가 상품비 CNY 2,500 | 동일 |
| 5/10 | 임시공 CNY 750 (△△무역 작업분) | `expenses`(TEMP_LABOR) + 주문 귀속 |
| 5/15 | 정산완료 처리 | `status=SETTLED`, 주문 잠금, 마진 확정 |

**결과**

```
총입금 CNY 25,000
총비용 CNY 19,250  (상품 17,500 + 검품 1,000 + 임시공 750)
최종마진 CNY 5,750   마진율 23.0%
```

> ✅ 5/3~5/10 의 지출이 각각 별개 행이 아니라 **하나의 주문으로 합산**되므로 중간 마이너스 마진이 발생하지 않습니다.
> ✅ 한국 계좌 잔액에는 전혀 영향을 주지 않습니다 (entity=CN).

## 시나리오 B. 일반통장 루트 (예치금 관리)

**상황**: ○○상사가 100만원씩 5회, 총 500만원 입금 → 이후 사용.

### B-1. 예치금 적립 (주문 미지정)

| 날짜 | 업무 | 시스템 처리 |
|------|------|------------|
| 4/1~4/20 | 100만원 × 5회 입금, `☑ 예치금으로 적립` 체크 | `receipts` 5건 (order_id = NULL) <br> `receipt_splits` = `DEPOSIT_GENERAL` <br> `deposit_ledger` `IN_RECEIPT` +1,000,000 × 5 |

**현재 상태**: ○○상사 예치금 잔액 5,000,000원

### B-2. 예치금 사용 (주문 발생)

| 날짜 | 업무 | 시스템 처리 |
|------|------|------------|
| 5/1 | 새 거래 등록 → ○○상사 / 일반통장 <br> `☑ 예치금에서 충당` 3,000,000원 <br> 적용환율 195.0 | `orders` 생성 <br> `receipts` (source=`FROM_DEPOSIT`, 3,000,000원, fx 195.0 → CNY 15,384.62) <br> `receipt_splits` = `SALES` <br> `deposit_ledger` `USE_ORDER` −3,000,000 |
| 5/3 | 상품대금 CNY 11,000 | `expenses` + 배분 |
| 5/6 | 대행통관비 200,000원 | `expenses`(CUSTOMS) + 배분 |
| 5/8 | 인건비 CNY 500 | `expenses` + 배분 |

**결과 (정산통화 KRW)**

```
총입금   3,000,000
상품비   2,145,000  (CNY 11,000 × 195.0)
통관비     200,000
인건비      97,500  (CNY 500 × 195.0)
총비용   2,442,500
최종마진   557,500   마진율 18.58%

○○상사 남은 예치금 2,000,000원
```

### B-3. 예치금 반환

| 업무 | 시스템 처리 |
|------|------------|
| 남은 200만원 중 50만원 고객에게 반환 | `deposit_ledger` `REFUND` −500,000 (**사유 입력 필수**) <br> `expenses`는 생성하지 않음 (비용 아님) <br> 계좌 출금은 별도 출금 전표로 기록 |

## 시나리오 C. 법인통장 루트 (세금계산서 전액 발행)

**상황**: ㅇㅇ산업에 상품 직접 납품, 500만원 입금, 전액 세금계산서 발행.

| 날짜 | 업무 | 시스템 처리 |
|------|------|------------|
| 5/1 | 새 거래 등록 → ㅇㅇ산업 / 법인통장 / 거래유형 `법인통장 전액발행` | `orders` (deal_type=CORP_FULL, accounting_class=상품매출) |
| | 입금 5,000,000원, 환율 195.0 | `receipts` + `splits`(SALES) |
| 5/4 | 중국 상품비 CNY 18,000 | `expenses` + 배분 (3,510,000원) |
| 5/6 | 대행통관비 250,000원 | `expenses` + 배분 |
| 5/7 | 기타비 80,000원 | `expenses` + 배분 |
| 5/10 | 세금계산서 생성 | `invoices` 자동 산출: <br> 대상금액 = 총입금 5,000,000 (TOTAL_RECEIPT) <br> vat_mode=INCLUDED → 공급가액 4,545,455 / 부가세 454,545 / 합계 5,000,000 |
| 5/10 | 발행처리 | `issue_status=ISSUED`, `issue_date`, 승인번호 입력 <br> `orders.invoice_status=ISSUED` |

**결과**

```
총입금 5,000,000 / 총비용 3,840,000 / 마진 1,160,000 (23.2%)
세금계산서: 공급가액 4,545,455 + 부가세 454,545 = 5,000,000
```

> 엑셀 법인통장 시트 뒤쪽의 **헤더 불명확한 부가세 열**이 여기서 명확히 분리됩니다.

## 시나리오 D. 사이트 결제 루트 ⭐ (가장 중요)

**상황**: ㅁㅁ社 고객이 사이트에서 1,100,000원 결제 (상품 100만원 + 수수료 10만원).

### D-1. 입금

| 업무 | 시스템 처리 |
|------|------------|
| 새 거래 등록 → ㅁㅁ社 / 사이트 <br> 총입금 1,100,000 <br> 상품예치금 1,000,000 / 수수료 100,000 | `orders` (deal_type=SITE_AGENCY, revenue_basis=**NET**) <br> `receipts` 1,100,000 <br> `receipt_splits`: `DEPOSIT_GOODS` 1,000,000 + `FEE` 100,000 <br> `deposit_ledger` `IN_RECEIPT` **+1,000,000 (GOODS_FUND)** |

**즉시 화면 표시**

| 항목 | 금액 |
|------|-----:|
| 총 입금액 | 1,100,000 |
| 상품구매 예치금 | 1,000,000 |
| 구매대행 수수료 | 100,000 |
| **중국 송금대기금** | **1,000,000** |

### D-2. 일부 송금 (60만원)

| 업무 | 시스템 처리 |
|------|------------|
| 해외송금 등록 → 600,000원 (환율 195.0 → CNY 3,076.92) <br> 배분: ORDER-...126 에 600,000 | `remittances` 생성 <br> `remittance_allocations` (order_id=126, alloc_krw=600,000) <br> `deposit_ledger` `USE_REMIT` **−600,000 (GOODS_FUND)** |

**화면 자동 갱신**

| 항목 | 금액 |
|------|-----:|
| 총 상품자금 | 1,000,000 |
| 송금완료 | 600,000 |
| **송금대기** | **400,000** |
| 주문 송금상태 | **일부송금(PARTIAL)** |

### D-3. 마진 계산

```
매출인식액(NET) = 수수료 100,000
회사부담비용    = 포장비 15,000   (상품대금은 예치금에서 나가므로 회사 비용 아님)
최종마진        = 85,000
마진율          = 85.0%  (수수료 기준)
```

### D-4. 세금계산서

```
거래유형 SITE_AGENCY → invoice_base = FEE_ONLY
대상금액 = 100,000 (총입금 1,100,000이 아님 ⭐)

vat_mode = EXCLUDED 인 경우: 공급가액 100,000 / 부가세 10,000 / 합계 110,000
vat_mode = INCLUDED 인 경우: 공급가액  90,909 / 부가세  9,091 / 합계 100,000
   ⚠️ 어느 쪽인지는 설정으로 지정 (프로그램이 임의 판단 안 함)
```

## 시나리오 E. 여러 고객 돈을 합쳐 한 번에 송금 ⭐

**상황**: 5/10 세 거래처의 송금대기금을 합쳐 1,000만원 송금.

```
해외송금 등록
  KRW 10,000,000 → USD 7,246.38 → CNY 51,282.05 도착
  실효환율 195.00 / 송금수수료 25,000

  배분:
   ○○상사   ORDER-2026-000128   7,000,000
   ㅁㅁ社    ORDER-2026-000126     400,000
   △△무역  ORDER-2026-000131   2,600,000
   ────────────────────────────────────────
   합계                        10,000,000  ✓ (= 송금액, 불일치 시 저장 차단)
```

**시스템 처리**
- `remittances` 1건 + `remittance_allocations` 3건
- `deposit_ledger` `USE_REMIT` 3건 (각 거래처 GOODS_FUND 차감)
- 각 주문의 송금상태 자동 재계산 (대기 → 일부/완료)
- 송금수수료 25,000원은 `expenses`(BANK_FEE) 로 생성, 배분은 선택 (미배분 시 운영비)

## 시나리오 F. 중국 운영비 월마감

| 업무 | 시스템 처리 |
|------|------------|
| 5월 급여 등록 (王小明 CNY 5,900 등) | `payrolls` 입력 → 확정 시 `expenses` 자동 생성 (SALARY / INSURANCE) |
| 임시공 CNY 750 — ○○상사 작업분 | `expenses`(TEMP_LABOR) + **주문 귀속** → 그 주문 마진에서 차감 |
| 임시공 CNY 600 — 창고 정리 | `expenses`(TEMP_LABOR) **미귀속** → 중국 운영비로 집계 |
| 사무실 월세 CNY 3,500 등 | `expenses`(OFFICE) |

**월 마감 시 대시보드 자동 반영**

```
주문마진 합계        18,450,000
− 중국 운영비        11,600,000
────────────────────────────────
= 최종 영업마진       6,850,000
```

## 시나리오 G. 금액 수정 / 취소

### G-1. 금액 수정 (진행중 주문)

```
5/3 상품비 CNY 15,000  →  CNY 15,500 으로 정정
1. 지출 상세 열기 → 금액 수정
2. **사유 입력 필수**: "공장 단가 정정"
3. 저장
   → change_logs: field=amount, old=15000.00, new=15500.00,
                  changed_by=박직원, changed_at=2026-05-12 14:22, reason=...
   → 주문 마진 자동 재계산
```

### G-2. 취소 (void)

```
잘못 입력된 송금 전표 취소
1. [취소] 버튼 → 사유 입력 "계좌번호 오류"
2. remittances.is_void = TRUE (행은 남음, 삭제 아님)
3. 연결된 deposit_ledger는 삭제하지 않고 **반대부호 상쇄행 추가**
   (append-only 원칙 유지)
4. change_logs: action=VOID 기록
```

### G-3. 정산완료 주문 수정

```
SETTLED 상태 → 전표 추가/수정 차단
MANAGER 이상이 [잠금해제] + 사유 입력 시에만 가능
change_logs: action=UNLOCK 기록 → 대시보드 "잠금해제 이력" 에 노출
```
