# 08. 변경이력·감사 설계

> **돈을 다루는 프로그램**이므로 "삭제하고 다시 계산"을 구조적으로 불가능하게 만듭니다.
> 업로드하신 엑셀에서 발견된 문제들(수식이 다른 행을 참조, 헤더와 실제 값 불일치)이 재발할 수 없는 구조를 목표로 합니다.

---

## 1. 무삭제(No-Delete) 원칙

| 대상 | 정책 |
|------|------|
| `orders`, `receipts`, `expenses`, `remittances`, `invoices`, `internal_transfers` | **물리 삭제 금지.** `is_void = TRUE` + 사유 |
| `deposit_ledger` | **DB 수준에서 UPDATE/DELETE 차단** (append-only). 정정은 반대부호 상쇄행 |
| `partners`, `accounts`, `deal_types` | 삭제 대신 `is_active = FALSE` |
| `change_logs` | INSERT 전용. 수정·삭제 권한 미부여 |

```sql
CREATE RULE deposit_ledger_no_update AS ON UPDATE TO deposit_ledger DO INSTEAD NOTHING;
CREATE RULE deposit_ledger_no_delete AS ON DELETE TO deposit_ledger DO INSTEAD NOTHING;
REVOKE UPDATE, DELETE ON change_logs FROM app_user;
```

## 2. 변경이력 기록

**기록 단위: 필드 하나당 1행**

| 필드 | 값 예시 |
|------|--------|
| table_name | `expenses` |
| record_id | `4821` |
| action | `UPDATE` |
| field_name | `amount` |
| **old_value (이전 값)** | `15000.00` |
| **new_value (변경된 값)** | `15500.00` |
| **changed_by (수정자)** | `박직원 (user_id=7)` |
| **changed_at (수정시각)** | `2026-05-12 14:22:03+09` |
| reason | `공장 단가 정정` |
| request_id | `a3f2…` (한 번의 저장 동작을 묶는 ID) |

### action 종류

| action | 시점 |
|--------|------|
| `CREATE` | 전표 생성 (전체 값을 JSON으로 기록) |
| `UPDATE` | 필드 변경 (변경 필드마다 1행) |
| `VOID` / `RESTORE` | 취소 / 복구 |
| `SETTLE` / `UNLOCK` | 정산 확정 / 잠금해제 ⚠️ |
| `IMPORT` | 엑셀 가져오기로 생성 (출처 시트·행번호 기록) |
| `LOGIN` / `EXPORT` | 접속 / 내보내기 (감사용) |

### 구현

저장 함수를 단일 게이트로 강제해 개발자가 빠뜨릴 수 없게 합니다.

```ts
await auditedSave({
  table: 'expenses',
  id: 4821,
  patch: { amount: 15500 },
  reason: '공장 단가 정정',   // 금액 필드 변경 시 필수 — 없으면 예외
  user: currentUser,
})
```

### 사유 필수 필드

| 테이블 | 필드 |
|--------|------|
| receipts | amount, **fx_rate**, receipt_date, partner_id |
| expenses | amount, **fx_rate**, category_id, payment_status |
| remittances | krw_amount, cny_arrival_amount, status |
| invoices | target_amount, supply_amount, vat_amount, issue_status |
| deposit_ledger | `ADJUST` / `REFUND` 행은 reason 없이 생성 불가 |

> **환율(`fx_rate`)을 사유 필수에 넣은 이유**: 엑셀에서는 환율이 수식 안에 숨어 있어 누가 언제 바꿨는지 알 수 없었습니다. 시스템에서는 환율 변경이 마진을 직접 바꾸므로 이력이 반드시 남아야 합니다.

## 3. 취소(VOID) 연쇄 규칙

```
송금 전표 취소
 ├ remittances.is_void = TRUE
 ├ remittance_allocations 유지 (이력)
 └ deposit_ledger 에 상쇄행 INSERT
      movement='ADJUST', amount_krw=+600,000
      reason='RM-2026-000012 취소에 따른 복원'
```

```
입금 전표 취소
 ├ receipts.is_void = TRUE
 ├ receipt_splits 유지
 ├ deposit_ledger 상쇄행 (예치금 분해가 있었던 경우)
 └ 주문 마진 자동 재계산
```

```
지출 전표 취소
 ├ expenses.is_void = TRUE
 ├ expense_allocations 유지 (집계에서 is_void 로 제외)
 └ 연결 주문 마진 자동 재계산
```

> 취소된 전표는 목록에서 **취소선 + 회색**으로 표시되며, `취소 포함 보기` 토글로 확인합니다.

## 4. 주문 잠금

```
OPEN (진행중)
  └─ [정산완료] → SETTLED
        · 하위 전표 추가/수정/취소 차단
        · settled_margin 에 마진 스냅샷 저장
        · change_logs: action=SETTLE

SETTLED
  └─ [잠금해제] (MANAGER 이상 + 사유 필수) → OPEN
        · change_logs: action=UNLOCK
        · 대시보드 "이번 달 잠금해제 N건" 배지로 노출
```

## 5. 계산 근거의 추적 가능성

엑셀에서 발견된 문제와, 시스템이 그것을 막는 방법입니다.

| 엑셀의 문제 | 시스템의 대응 |
|------------|--------------|
| 환율이 수식(`=C3/218.22`)에만 있어 집계·검증 불가 | 환율을 **데이터 컬럼**으로 저장. 목록에서 정렬·필터 가능 |
| 헤더 `환율적용 192`와 실제 값 218이 불일치 | 화면 라벨과 저장값이 같은 필드에서 나옴. 불일치 자체가 불가능 |
| 법인통장 319행 수식이 **다른 행(E321)을 참조** | 집계가 관계(FK)로 이뤄져 다른 행 참조가 구조적으로 불가능 |
| M열 헤더가 없어 정체를 알 수 없음 | 모든 필드에 이름·타입·설명이 붙음 |
| 마진율 분모가 지출금액인지 입금액인지 알 수 없음 | 두 지표를 라벨과 함께 나란히 표시 |
| 값을 붙여넣으면 수식(환율)이 사라짐 | 계산 결과가 아니라 **입력값**을 저장 |
| 합계가 기본급/실지급 중 무엇인지 불명확 | 집계 기준을 문서와 화면에 명시 (`실지급 기준`) |

### 대시보드 수치의 재현 가능성

| 요구 | 구현 |
|------|------|
| "작년 5월 대시보드를 지금 봐도 같아야 한다" | 모든 집계가 **전표 발생일 기준** → 재계산 시 동일 |
| "환율이 바뀌어도 과거 수치가 변하면 안 된다" | 환산액을 전표에 저장 → 사후 환율 변경 영향 없음 |
| "정산완료 주문 마진은 고정되어야 한다" | `settled_margin` 스냅샷 + 재계산값 불일치 시 경고 |

**월 마감(선택 기능)**
월 단위 `period_close` 처리 시 해당 월 전표 전체 잠금. 마감 후 수정은 OWNER 승인 + `UNLOCK` 이력.

## 6. 접근 감사

| 항목 | 기록 |
|------|------|
| 로그인 / 로그아웃 | user, IP, 시각 |
| 엑셀 내보내기 | 대상 화면, 행 수, 사용자 |
| 급여 화면 조회 | OWNER/MANAGER만 접근, 조회 이력 기록 |
| 잠금해제 | 별도 알림 (대시보드 배지) |
| 엑셀 가져오기 | 배치 ID, 생성 건수, 되돌리기 여부 |
